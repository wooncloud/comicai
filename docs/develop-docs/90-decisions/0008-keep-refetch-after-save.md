# ADR-0008: 편집기 저장 뒤 목록 재조회를 유지한다 (T-06 보류)

- 상태: Accepted
- 날짜: 2026-09-22

## 컨텍스트

편집기에서 도형(컷·말풍선·텍스트·직선)을 고치면 `use-shape-sync.ts` 가 1.5초 디바운스 뒤 PATCH/POST/DELETE 를 보내고,
성공하면 **그 종류의 목록을 통째로 다시 GET** 한다. T-06 은 "PATCH 응답 DTO 로 상태를 고쳐 재조회를 없애자" 였다.

설계 단계(agy, 2026-09-22)에서 확인한 사실:

- **API 는 이미 네 종류 모두 POST(201)·PATCH(200) 에서 완성된 DTO 를 돌려준다.** 웹만 그 응답을 버린다.
  → 하게 된다면 **웹 단독 변경**으로 된다. 배포 순서 문제가 없다.
- 편집기 도형 데이터는 react-query 가 아니라 `page.tsx` 의 `useState` 에 있다.
- 재조회가 지금 **덤으로** 지키고 있는 것: 부모 `items` 최신화(역방향 투영이 옛 좌표로 덮지 않게), 서버가 채우는 값
  (`order` 채번, `style` 기본값 병합, 컷의 presigned URL), 다른 탭의 변경, 백그라운드 렌더 결과, 어긋난 상태의 자가 치유.

## 결정

**지금은 하지 않는다.** 재조회를 유지한다.

- **얻는 것이 작다.** 재조회는 디바운스 때문에 편집 중에도 최대 1.5초에 한 번, 고친 **그 종류만** 읽는다. 한 페이지 도형은
  보통 수십 개라 응답이 수 KB 다. 설계서는 "S3 presigned URL 생성 부하" 를 근거로 들었지만, `presignDownload`
  (`apps/api/src/storage/storage.service.ts`)는 `getSignedUrl` 로 **로컬에서 서명만** 계산한다 — 네트워크 호출이 없다.
- **건드리는 곳이 가장 예민하다.** 같은 날 T-04(역방향 투영 통합)와 T-03(층 순서)으로 겨우 안정시킨 동기화 엔진이다.
  위험 13개(R-1~R-13)를 새 테스트로 지켜야 하고, 다중 탭 반영·자가 치유를 포커스 재조회 같은 새 장치로 대신해야 한다.

## 다시 볼 때

다음 중 하나가 생기면 설계서(아래)를 그대로 꺼내 시작한다.

- 한 페이지 도형이 수백 개가 되어 재조회 응답이 커질 때
- 사용자가 늘어 편집 트래픽이 서버 부하로 보일 때
- 저장 직후 재조회 때문에 체감 지연·깜빡임이 보고될 때

설계서: 에이전트 우편함의 `_mail/T-06/plan.md` (저장소 밖). 핵심 요지는 위 "컨텍스트" 에 옮겨 두었다 —
웹 단독 변경, 성공 시 응답 DTO 로 `items` 를 불변 갱신, **최종 실패 시 재조회는 유지**, 포커스·온라인 복귀 재조회를 새로 둔다.
